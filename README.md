## 1. 第1章：開発思想とコア・コンセプト (CORE VISION & PHILOSOPHY)
1.1: 言語の定義と具体的な用途（どこに使うか）
C*（シー・スター）は、世界中に存在する膨大な既存C++システムを「1文字も型システムを破壊せず」に完全安全化（Modernize）し、 Rustと同等のメモリ安全性を「追加の実行時オーバーヘッド完全ゼロ（0%）」かつ「人間の認知負荷を極小（1.2割）」で両立するために設計された、次世代のシステムプログラミング言語（C++の静的安全拡張規格）である。
【主な想定用途（Target Domains）】
インディーゲームおよびトリプルA（AAA）ゲーム開発： 1ミリ秒の遅延、数バイトのメモリ肥大化、GC（ガベージコレクション）によるスパイク（カクつき）が許されないゲームループ、物理演算、描画パイプライン（DirectX 12 / Vulkan）。
HPC（ハイパフォーマンスコンピューティング）＆ AI推論エンジン： 大規模な行列計算、CUDA/C++混在環境、CPUのSIMD（自動ベクトル化）を極限まで回す必要があるディープラーニングの低レイヤランタイム。
レガシー大企業の基幹システム救済： 金融、自動車（車載OS）、組み込み、航空宇宙など、数百万行のC++コードが存在し、Rustへの全面書き換えコストが「地獄の数兆円」になるため、C++の資産をそのまま活かしてホワイトハウスの安全基準（メモリ安全性の義務化）を満たさねばならない領域。
1.2: 組み合わせる要素・コア技術
Cは、全く新しいスタンドアロンのコンパイラを新設するのではない。既存の強力なオープンソースインフラである 【Clangフロントエンド】 と 【LLVMバックエンド】 のソースコードを内側から直接「ハック・改造」し、コンパイラの最適化パス（Optimization Pass）そのものにC独自の静的解析レイヤーをインジェクションする手法をとる。
また、開発環境のエディタ体験をサクサクに保つため、【LSP（Language Server Protocol）の非同期文脈解析キュー】を組み合わせる。
1.3: なぜ実現できるのか（主従関係の逆転と決定論の理屈）
Rustは「人間を機械（コンパイラ）の奴隷にする」ことで安全性を担保した。人間に難解な文法（ファイル全体に及ぶ明示的なライフタイム 'a や所有権、参照剥ぎ取りのルール）を必死に覚えさせ、人間の脳に膨大な「認知負荷」をかけることで安全性を達成している。
対してC*は、「人間ファースト（主従関係の逆転）」を貫く。人間はポインタのサイズや性質（Read/Write）といった物理的境界を、バグが起きそうな「その1行の式（Expression）」にほんの数文字添えるだけ（1.2割の心地よい責任）でよい。
【なぜ全自動エスパーではなく、1.2割の負担が必要なのか】
関数を跨いだ生ポインタのエイリアス解析（そのポインタが指す先の正確なメモリ領域と生存期間の追跡）は、計算機科学における「停止性問題（Halting Problem）」の壁にぶつかるため、コンパイラが100%全自動で推論（エスパー）することは数学的に不可能である。
だからこそC*は、機械に無謀な推論をさせるのをやめ、「人間がサイズという事実（不変量）を型システムに直接注入（契約）し、それを受けた決定論的コンパイラが残りの8.8割の泥臭い数理証明とコード生成を執行する」というアプローチを取る。これにより、確率論的なAIの推論にビルドの成否を委ねるという決定論的コンパイラにあるまじき矛盾（v10.0.0でパージされた仕様）を完全に解決し、物理法則に適合する形で安全性を確定させている。

## 2. 第2章：【速度 vs 安全】の解決（局所的ガード式 safely 構文）
2.1: 仕様と用途（どこに使うか）
すべてのポインタをファットポインタ化（構造体化してポインタの横にサイズ情報を抱え込ませる仕様）すると、メモリレイアウトが変化して外部C++バイナリ（OpenCVやWindows API、DirectX等）とのバイナリ互換性（ABI）が100%崩壊する。また、ポインタの上位ビットにサイズ情報を無理やり埋め込む仕様（Tagged Pointer / MMUハック）は、現代のCPUハードウェア例外（一般保護違反：General Protection Fault）を誘発し、最悪のシステムクラッシュの原因となる。
C*はこれを解決するため、既存のC++コードの真ん中に、危険な配列アクセスやポインタのデリファレンスが発生する「その1行の式」に対してのみ、以下の標準属性構文を用いて局所的なガードを展開する。
cpp
// ==== [C*の具体的な記述仕様] ====

// ① 通常の1次元配列アクセス（人間負担度1.0割）：読み取りの性質「R」とサイズを明示
[[cstar::restrict]] int value = safely<R>(raw_ptr[index], size);

// ② 魔境の多次元配列アクセス（人間負担度1.2割）：次元数「2」と読み書き「W」、各境界サイズを明示
[[cstar::restrict]] int val2 = safely<2, W>(matrix[x][y], width, height);

コードは注意してご使用ください。
【用途】
ゲームの毎フレーム回る最深部のループ内におけるテクスチャピクセルアクセス、AIの行列要素の書き換えなど、「速度低下が1ナノ秒も許されないが、範囲外アクセス（Out of Bounds）による脆弱性を絶対に出したくない極限の計算ライン」に使用する。
2.2: 組み合わせる要素・技術
Clangフロントエンド（フェーズ0・インメモリーASTトランスフォーム）： 既存の標準C++パーサー（Parser）が「C*規格のsafelyなんて構文は知らない」とパニックを起こしてビルドエラーを吐くのを防ぐため、コンパイラ最初期段階（プリプロセッサ通過直後）のメモリ内で、C++標準の属性構文（Attribute）と即時実行ラムダ式へと構文を事前トランスフォームする技術。
LLVMバックエンド（Scalar Evolution / Value Tracking パス）： ループの変数（インデックス）が、コンパイルタイム（ビルド時）に数理的にどこまで到達するかを計算するLLVMの強力なループ解析・数理証明エンジン。
CPU条件付き移動命令（cmov）： レジスタ間でデータを条件付きでコピーする、現代のCPUがサポートする「分岐予測を必要としない最速の機械語命令」。
2.3: なぜ実現できるのか（数理証明によるチェック命令の「完全蒸発」の理屈）
Rustを含む従来の安全な言語は、安全性を担保するために「実行時（ランタイム）に毎回、インデックスが範囲内にあるかをチェックするif文」を盲目的に挿入する。これにより、CPUのパイプラインがストールし、ゲームやAI計算で最も重要な「SIMD化（ループの自動ベクトル化：複数のデータを1命令で一括処理するCPUの最高速機能）」が100%解除（崩壊）され、速度が数倍〜数十倍遅くなる。
C*が追加コストゼロ、すなわち「生のC++と同等、あるいはそれ以上の神速」を物理的に達成できる理屈は、「人間がサイズを明示してくれたおかげで、コンパイラがビルド時に『安全か不安全か』を100%決定論的に白黒つけられるようになったから」である。
人間が明示した size という「絶対に動かない物理的境界」の不変量を基に、LLVMバックエンドの数理証明パスが「このループ内のインデックスは、絶対に size を超えない」とビルド時に数理的（フォーマル・ヴェリフィケーション）に100%証明できた領域については、範囲チェックのためのif文や例外処理の機械語命令を1バイトも出力せず、完全に消滅（蒸発）させる。
証明できた領域は、チェックが最初から「存在しない」ため、オーバーヘッドは物理的に0%であり、SIMD化が100%強制解放される。これが「速度と安全」が物理法則をねじ伏せて両立する理屈である。
2.4: 具体的なC*のコンパイラルール
コンパイラ（cstar-clang++）は、人間が記述した safely 構文を検知した際、以下の厳格な内部ルールに従って処理を実行しなければならない。
【ルール2.4.1：フェーズ0 構文トランスフォームルール】
フロントエンドのSemaExpr層に到達する前のインメモリ段階において、人間が書いた safely 式を、Clangの既存エンジンが100%合法的なC++として解釈できる以下の「属性付き即時実行ラムダ式」へ強制変換（文字列・AST置換）しなければならない。
cpp
// ⚙️ コンパイラが内部で自動置換する「100%合法的な標準C++表現」
int value = ([&]() [[cstar::safe_bounds(raw_ptr, size)]] {
    return raw_ptr[index];
})();

コードは注意してご使用ください。
このルールにより、大企業の巨大なビルドシステム（CMake等）のパイプラインや、既存のClangコアエンジンに1ミリの修正も入れることなく、C*の仕様をパススルーで通過させる。
【ルール2.4.2：noalias（unset __restrict 相当）の自動解放ルール】
人間が safely<R>（Read専用）または safely<W>（Write専用）を明示したポインタに対し、コンパイラは「この式が評価される瞬間、このポインタは完全に孤立しており、他のどのメモリ空間とも重なって（ポインタ不倫して）いない」と判定する。
LLVM IRの出力段階において、対象ポインタのデータパスに対し、ネイティブな noalias および readonly（Rの場合のみ）属性を強制付与しなければならない。これにより、通常のC++であれば熟練の職人が血眼になって手動チューニングしなければ発火しなかった「CPUレジスタへの極限の並列最適化（SIMD化）」をバックエンドで自動的に発火させる。
【ルール2.4.3：多次元配列のフラット置換ルール】
safely<2, W>(matrix[x][y], width, height) のように次元数「2」が明示された多次元アクセスを検知した場合、プリプロセッサはエイリアス解析を完全にパス（スキップ）し、一瞬で (x * height) + y のような「1次元のフラットな超高速数理変換式」へと、単純なインライン置換を行わなければならない。これにより、多次元ポインタの解析に伴うコンパイラのフリーズ・無限ループリスクを物理的に消滅させる。
【ルール2.4.4：ループ境界分離（Loop Bounds Splitting）ルール】
コンパイラは、最深部の実行ループの「内部」に動的なチェック命令（cmovやif文）を1文字も配置してはならない。
代わりに、ループが回る「実行直前（ループの外側）」において、インデックスの開始（Start）から終了（End）までの全可動範囲が size 内に安全に収まっているかを1回だけ一括プリチェックする分岐コード（LLVM IRパス）を裏で自動生成しなければならない。
cpp
// ⚙️ 【ルール2.4.4に基づきコンパイラが裏で出力するC++等価コードの構造】

// ループの実行直前に、外側で1回だけ一括検証
bool __cstar_loop_safe = (loop_start >= 0 && loop_end < static_cast<int>(size));

if (__cstar_loop_safe) {
    // 🛡️ 【安全ライン（9割以上の通常ケース）】
    // チェック命令が1バイトも存在しない、完全に「裸の生C++ループ」へ突入。
    // 障害物がゼロなため、LLVM Loop Vectorizerの自動ベクトル化が100%発火し、
    // 生のC++と同じクロック（SIMD）で爆走する。
    for (int i = loop_start; i < loop_end; ++i) {
        // [完全に障害物のないネイティブ最高速処理]
        process(raw_ptr[i]); 
    }
} else {
    // ⚠️ 【危険ライン（動的グレーゾーンのフォールバック）】
    // 万が一、実行時に範囲を超えるリスクがある場合のみ、こちらに落とす。
    for (int i = loop_start; i < loop_end; ++i) {
        // CPUが最速で処理できる cmov 命令（三項演算子）によるインライン・バウンズガード
        bool __in_bounds = (i >= 0 && i < static_cast<int>(size));
        process(__in_bounds ? raw_ptr[i] : (throw std::out_of_range("C* Bounds Target Violated"), raw_ptr[0]));
    }
}

コードは注意してご使用ください。
このルールにより、安全性を担保しながら、最深部ループ内のオーバーヘッドを物理的に「完全消滅」させる。
## 3. 第3章：【互換性 vs 安全】の解決（関数境界 ABI と safe_ptr）
3.1: 仕様と用途（どこに使うか）
C++において、生の生ポインタ（int* ptr）が関数境界（関数の引数や戻り値）をまたいだ瞬間、そのポインタが指すメモリの「有効サイズ」や「寿命」の情報は規格上完全に消失する。呼び出された側の関数から見れば、それが1要素を指すのか、100万要素の配列の先頭を指すのかを静的に知る術がない。
C*は、ポインタ自体のメモリ構造（8バイトの生データ）を1ビットも変えてファットポインタ化することなく、この関数境界のブラックボックス化を解決するため、以下の「型アノテーション属性」仕様を強制適用する。
cpp
// ==== [C*の具体的な関数境界記述仕様] ====

// ① 引数ポインタに対し、同一の引数リスト内にある「サイズ変数 N」と紐づける型アノテーション
void process_vector(cstar::safe_ptr<int, "N"> raw_ptr, size_t N) {
    // この関数内部において、raw_ptr は自動的に「サイズ N」の物理的境界を持つものとして扱われる
    [[cstar::restrict]] int value = safely<R>(raw_ptr[index], N);
}

コードは注意してご使用ください。
【用途】
ゲームエンジン内の描画コンテキストをまたぐテクスチャバッファの受け渡し、物理演算ライブラリ（外部のC++やC*で記述された静的/動的ライブラリ）に関数引数として生配列のポインタを高速に引き渡すラインなど、「ファイルやコンパイル単位（Translation Unit）をまたいでポインタを安全にバケツリレーさせたい全ての境界」に使用する。
3.2: 組み合わせる要素・技術
現代C++標準のテンプレートエイリアスと属性（Attribute）： cstar::safe_ptr 自体はC++の標準的な構造体ラッピング技術であり、中身はプレーンなポインタのままであるが、コンパイラに対してコンパイルタイムの不変量契約（Contract）を通知する目的で組み合わせる。
LLVM IR引数インジェクション（LLVM Argument Injection）： C*同士の内部関数である場合に限り、LLVM IR（中間表現）の生成パスにおいて、関数の引数リストの末尾にコンパイラが裏で隠し引数を暗黙的に付け足す低層コード生成技術。
3.3: なぜ実現できるのか（「コンパイルタイム・ペアリング」と「ABI完全隔離」の理屈）
これまでの安全な言語（Rust等）は、ポインタとサイズをセットにした構造体（ファットポインタ）を関数の引数としてスタックやレジスタに積むため、既存のC++バイナリと完全に通信（ABI互換）できなくなる。また、旧C*仕様にあった「ポインタの上位16bitにサイズを埋め込む（Tagged Pointer）」手法は、CPUのハードウェア仕様と衝突して一般保護違反のクラッシュを招いた。
C*が「ポインタの物理構造はプレーンな8バイトのままで、関数をまたいでサイズを追跡できる」理屈は、「関数を呼び出す側（Caller）と呼び出される側（Callee）の間で、サイズ変数の静的・動的な対応関係（ペアリング）をコンパイラが厳密に証明・同期するから」である。
コンパイラは、関数定義の cstar::safe_ptr<int, "N"> という契約を検知すると、ビルド時に「このポインタのサイズ不変量は、変数 N の値と完全に同一である」という絶対の数理ルールを型システムに注入する。
呼び出し側（Caller）がポインタを渡す際、そのポインタの実際の確保サイズ（Allocation Size）と、引数に渡す N の値が一致しているかをデータフロー解析でクロスチェックする。物理的なメモリレイアウト（ポインタのビット）を1ミリも汚さないため、CPUレベルでのハードウェア例外は100%発生せず、追加の実行時オーバーヘッドも完全ゼロ（0%）が達成できる。
3.4: 具体的なC*のコンパイラルール
コンパイラ（cstar-clang++）は、関数境界におけるポインタアクセスを処理する際、以下の厳格な内部ルールに従わなければならない。
【ルール3.4.1：LLVM引数インジェクションルール】
コンパイラは、関数のシンボルをLLVM IRへエミット（出力）する際、その関数がCソースコード内で完結している内部関数（C同士の通信）である場合に限り、LLVM IRレベルで引数の末尾に size_t __cstar_hidden_size という隠しサイズ引数を全自動でインジェクション（挿入）し、レジスタやスタックを通じて安全情報のバケツリレーを執行しなければならない。
【ルール3.4.2：外部C++ ABI国境線自動識別・ストップルール】
コンパイラがAST（抽象構文木）解析時において、呼び出す対象の関数がソースコードのない外部C++ライブラリ（OpenCVやWindows API等）またはレガシーC++で記述された「外の世界の関数」であると判定した場合、ルール3.4.1の隠し引数インジェクションをその場で物理的に完全停止（自動ストップ）しなければならない。
外部関数に対しては、構造体化されていない純粋な8バイトのネイティブ生ポインタのみを引き渡すことで、外部ABIのパディング規則やレジスタ割り当て（x86_64 SysV ABI等）との衝突を物理的に遮断する。
【ルール3.4.3：外部から戻ったポインタの「汚染マーキング」ルール】
外部C++関数から戻り値として生ポインタ（int*）を受け取る際、コンパイラはそのポインタのサイズ・寿命情報が完全に消失したと判断し、内部メモリ（Sema層のステート）上でそのポインタを 「汚染ポインタ（Untrusted Pointer）」 として厳格にマーキングしなければならない。
【ルール3.4.4：汚染ポインタの静的アクセス拒否ルール】
マーキングされた「汚染ポインタ」に対し、人間が再度 safely 式、または cstar::safe_ptr への明示的なキャストによって「境界サイズ」を再宣言（再契約）しない限り、そのポインタに対する中身の読み書き（デリファレンス、配列アクセス）をコンパイラは静的に100%拒否（コンパイルエラーを出力）し、バイナリの生成を強制停止しなければならない。
これにより、旧世界から来た正体不明のポインタが、C*の安全圏を物理的に破壊するのを水際で完全に防衛する。

## 4. 第4章：【並列速度 vs データレース】の解決（マルチスレッド restrict 属性）
4.1: 仕様と用途（どこに使うか）
マルチスレッドプログラミングにおいて、複数のスレッドが同一のメモリ領域に対して同時にアクセスし、少なくとも1つが書き込みを行う状態（データレース：Data Race）が発生すると、メモリの未定義動作やデータの破損、TOCTOU（検査と複製の時間差）脆弱性を招く。
C*は、通常の変数アクセスをすべて一律で重いアトミック命令（AtomicRmw / LOCKプレフィックス）に格上げしてCPU速度を数十倍遅くする仕様（v2.0.0の頃の欠陥）を完全に排除する。代わりに、以下の「クリティカルセクションの明示的孤立」仕様を適用する。
